# Claude Code startup performance

On November 19, 2026, the last 12 MacBook ClaudePlus service logs contained a proxy-ready marker. Their creation-to-last-write spans were 50 to 77 seconds, with a median of 57.5 seconds. The spans include the server's startup output and give upper bounds on readiness from log creation. ClaudePlus takes its launcher lock before creating the log and gives the service up to 120 seconds to listen. These historical samples give no per-provider timing.

The critical path includes provider discovery, optional Switchyard preflight, native patch preparation, and starting the listener. An enabled provider previously waited for each earlier provider in the registry to finish. Catalog requests can spend 10 seconds on standard API or ChatGPT plan discovery and up to 20 seconds on individual Copilot requests. Multiple accounts and fallback requests add further latency. [Launcher](../scripts/claudeplus.py) · [Proxy startup](../src/http-proxy/index.ts) · [Catalog refresh](../src/registry/refresh-models.ts)

Leverframe now refreshes up to three independent provider catalogs concurrently. It keeps the registry order of the results and the sequential refresh inside each provider's account list. The proxy still waits for the required fresh catalog before offering external routes. An isolated test holds four provider requests open, confirms the fourth starts only when a slot opens, and confirms a provider error does not discard the others' successful catalogs. [Concurrency test](../tests/provider-refresh-concurrency.test.ts)

An isolated MacBook run used four fake provider responses with a 250 ms delay each. Serial refresh took 1,207 ms and bounded refresh took 628 ms, including registry publication. This measures catalog refresh in a fixture. Live startup also depends on account count, network latency, routing preflight and patching.

The first MacBook launch after installing the concurrent refresh build took 71 seconds from creation of the Leverframe log to creation of the Claude settings file. That interval ends before Claude Code starts and excludes time waiting for the launcher lock.

ClaudePlus records provider catalog loading, routing setup, Claude preparation, and proxy listener and certificate setup in its session's `leverframe.log`. Search for `[leverframe startup]` in the path ClaudePlus prints when it launches. Compare repeated launches with the same providers and accounts. Time spent waiting for the launcher lock and Claude Code's own startup fall outside these stage measurements.

The next measured MacBook launch spent 2.072 seconds loading the provider catalog, less than 1 millisecond setting up routing, 0.883 seconds preparing Claude Code, and 52.173 seconds starting the proxy and setting up certificates. The last measurement includes adapter startup, which checks stored execution checkpoints and tool ledgers before opening its listener. The local execution store occupied 5.6 GB at the time of inspection. The measurement does not isolate the execution scan from the rest of proxy startup.

A read-only run of the same execution scan took 44.5 seconds on that store. The scan only assembled a diagnostic report. Regular proxy and gateway launches now skip the scan. Debug startup retains the report, and the request path still checks the relevant stored state when it resumes an execution. The HTTP proxy opened both listeners and generated certificates in 80 milliseconds in an isolated fixture. That measurement excludes live provider discovery, Claude preparation, and the time Claude Code itself takes to open.
